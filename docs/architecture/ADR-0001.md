# ADR-0001 — One offline application, stable routes, protected historical identity

**Status:** Owner-approved architectural constraints, Phase 00 reconciliation (2026-10-31). Later-phase acceptance is NOT implied.

## Decision
Preserve the actual offline Windows `.NET 10` WPF/WebView2 host, local RTL HTML/CSS/JS and validated C# bridge, SQLCipher SQLite with a randomly generated protected Windows DPAPI key. Keep four post-login destinations: الرئيسية / التمام الشهري / الإدارة / الإعدادات; initialization and Login precede them.

Use the **69** manifest entries and their stable `routeKey` values rather than assuming sequential IDs: `screen_001`–`screen_019` plus `screen_021`–`screen_070`. `screen_020` is permanently retired; no duplicate Reports route. `screen_025` is the only individual/group Report, `screen_026` export, `screen_070` one-person AddPerson under Edit Names; `screen_002` is the read-only Automatically Prepared register and `screen_003` its protected revision. `screen_069` keeps the old technical key `EightPmScheduler` but performs the **configurable default 08:00** automated preparation, NOT a 20:00 auto run.

Technical identity is permanent (`PersonId`, `SiteId`, `StatusId`, `UserId`); visible Personnel No. (ع) is numeric **4–70 digit TEXT** retaining leading zeros. A verified RETURN of the same human reuses original PersonId; an expressly approved DIFFERENT human replacing one DISMISSED person's number receives an independent NEW PersonId and absolutely none of that prior person's historical evidence. Active-number collisions/ambiguities block automated merge. Use effective-dated historical snapshots, not current display text, for monthly/report/audit facts. Never overwrite canonical history.

The founder is a single `GeneralAdministration` account with **optional** full name and permanent `LinkedPersonId=NULL` (no later linking to roster). Other account roles are validated server-side; both administrations may perform seven-day missing-attendance catch-up and visible-only audit edit/hide, with Supervisor denied.

Scheduler policy: **08:00** configurable auto attendance with yesterday's legitimate status or approved fallback, limited automatic catch-up to **yesterday only** and eligible today, durable idempotent ledger; separate **20:00** configurable manual-attendance lock and midnight calendar-day closure. Owner's **2026-10-31 override** mandates independent audited saving of automatic time, lock time and fallback (successes retained if one fails), not old all-or-nothing transaction. Authorized movements may occur after attendance commit/lock with preserved history.

Daily encrypted backup defaults to **16:00**. Use `E:\AlTamamAlYawmi\Backups` only if writable, otherwise report failure and show Windows folder selection. Both direct-run Portable and Installer share the SAME per-Windows-user `%LOCALAPPDATA%\AlTamam` without implicit migration, relocation or deletion. DPAPI alone cannot recover on a different PC: secure portable recovery material, staged validated restore, reauthentication, native confirmation, writer quiescence, atomic switch and rollback require real Windows checks. Destructive restore remains unavailable until accepted.

## Phase ownership and change gates
Retain **00–15**: 00 inventory, 01 solution/CI, 02 encrypted temporal data, 03 accounts, 04 native UI/bridge, 05 roster, 06 attendance/dashboard, 07 automatic scheduler/lock, 08 movements/monthly, 09 unified report, 10 Excel, 11 audit, 12 backup/settings, 13 real Windows tests, 14 four packages, 15 final delivery. There is no parallel screen roadmap or new document-approval gate.

Ordinary changes use feature branches/PRs: Windows Core and Windows Release independent parallel checks on the same head SHA; Release executes actual tests BEFORE building x86/x64 Portable ZIP and Installer EXE plus real SHA-256. Do not merge on failure, missing check or missing artifact. Cache NuGet **inputs** only; measure runner wait, restore, compilation, testing and packaging separately across successful runs; no cached binaries/test results from other SHAs. Actual clean offline Windows and cross-machine restore acceptance belong to later phases.

## Consequences and deferred mismatch inventory
Only the inventory/documentation is approved in Phase 00. Preserve all working UI/bridge behavior and old routeKey values. The current `screen_003` breadcrumb contains obsolete «غير المحضرين», and `screen_026` UI/manifest title is singular while the approved report/export scope is individual AND group; both are documented for their owning phases rather than silently patched in inventory. The legacy `EightPmScheduler` identifier does not revive superseded old 20:00 automatic completion. Prior audit reports are historical, not new active instructions; old Jules/Termux file dependencies are not required. Current delivery cannot be declared production-ready on a manifest check alone.
